FB.Set( of T ) -- a hash set
===========================

    #include once "fb/set.bi"            ' or "containers.bi" for all four
    using FB

    dim seen as Set( of long )

    if seen.Add( 42 ) then print "first time"

    for each x in seen
        print x
    next

Add returns FALSE when the element was already present, which is what makes

    if seen.Add( x ) then ...

the natural spelling of "process each thing once".


MEMBERS
-------

    Count( ) as long                          O(1)
    IsEmpty( ) as boolean                     O(1)
    Capacity( ) as long                       O(1)

    Add( byref v as T ) as boolean            avg O(1)  FALSE if already present
    Contains( byref v as T ) as boolean       avg O(1)
    Remove( byref v as T ) as boolean         avg O(1)  TRUE if something went

    Clear( )                                  O(n)
    Reserve( byval n as long )                O(n)

    UnionWith( byref other as Set( of T ) )        O(|other|)
    IntersectWith( byref other as Set( of T ) )    O(n)
    ExceptWith( byref other as Set( of T ) )       O(|other|)

    Items( ) as Array( of T )                 O(n)      snapshot
    GetIterator( ) as SetIterator( of T )     O(1)

The three set operations modify the receiver in place and leave the operand
untouched:

    dim a as Set( of long )      ' { 1, 2, 3, 4, 5 }
    dim b as Set( of long )      ' { 4, 5, 6, 7, 8 }

    dim u as Set( of long ) = a
    u.UnionWith( b )             ' { 1..8 }, a unchanged

    dim n as Set( of long ) = a
    n.IntersectWith( b )         ' { 4, 5 }

    dim e as Set( of long ) = a
    e.ExceptWith( b )            ' { 1, 2, 3 }

IntersectWith collects the doomed elements first and removes them afterwards.
Removing while walking the set's own slots would leave tombstones in the middle
of a chain being probed.


THE HASH CONTRACT
-----------------

An element type T must satisfy:

    FB.HashOf( v )       must resolve
    v = v                must compare
    EQUAL ELEMENTS MUST PRODUCE EQUAL HASH CODES

The converse is not required. Overloads are supplied for every built-in type;
strings hash by CONTENT, and +0.0 / -0.0 hash the same because they compare
equal.

A user type is made usable by RE-OPENING the namespace:

    type Tag
        as long id
    end type

    operator = ( byref x as Tag, byref y as Tag ) as boolean
        return x.id = y.id
    end operator

    namespace FB
        function HashOf overload ( byref k as Tag ) as ulongint
            return HashOf( k.id )
        end function
    end namespace

Derive the hash only from the fields '=' compares.

An element type with no overload fails at the INSTANTIATION site:

    error 99: No matching overloaded function, HASHOF()
      in instantiation of 'Set( of NOHASH )'

Source: src/inc/fb/hash.bi


DO NOT MODIFY AN ELEMENT IN PLACE
---------------------------------

The iterator's Value( ) is byref, so 'for each byref' compiles:

    for each byref x in seen
        x += 1                   ' DON'T
    next

Changing an element changes its hash, and it can never be found again -- it
still occupies a slot, Count( ) still counts it, and Contains( ) returns false
for both the old value and the new one. Remove and re-Add instead.

The byref binding is allowed rather than blocked because the container cannot
tell a harmless read-through from a mutation, and blocking it would also block
passing an element byref to a function.


ITERATION
---------

ITERATION ORDER IS UNSPECIFIED and changes across insertions. It is not
randomised per process.

Items( ) is a SNAPSHOT, returned as Array( of T ). Changing it does not change
the set -- which is the safe way to remove while "iterating":

    dim all as Array( of long ) = s.Items( )
    for i as long = 0 to all.Count( )-1
        if unwanted( all[ i ] ) then s.Remove( all[ i ] )
    next


IMPLEMENTATION
--------------

A Map with the value machinery removed rather than a wrapper around one, so a
Set costs ONE slot per element instead of two.

Open addressing with linear probing, power-of-two capacity, tombstones on
removal, load factor 0.75, rehash doubles. Removal leaves a tombstone rather
than an empty slot, because probing stops at the first EMPTY slot and blanking
would cut the chain. Rehashing drops tombstones, which is what stops an
add/remove churn loop from filling the table with them.

Source: src/inc/fb/set.bi


OWNERSHIP AND COPYING
---------------------

The set owns its storage. COPY AND ASSIGNMENT ARE DEEP. That is expensive and
there is no move constructor in the language to avoid it; pass sets BYREF where
it matters. A Set( of T ptr ) frees the TABLE, not the pointees.


ITERATOR INVALIDATION
---------------------

Nothing detects a violation.

    Add causing a rehash                        all iterators invalidated
    Remove                                      all iterators invalidated

Use Items( ) to take a snapshot if you need to mutate while walking.


TESTS
-----

src/tests/generics/container-set.bas is exhaustive: every member, empty / one /
many states, Add's novelty return, removal and tombstones, churn, the growth
path, all three set operations including every degenerate case (empty operand,
empty receiver, with itself, disjoint), the Items snapshot, FOR EACH in both
binding forms, element types including strings (with the empty string and a
run-time-built string), doubles with +0.0 / -0.0, and a user type with its own
HashOf, deep copy and assignment independence in both directions, and destructor
balance with a counting element type.

Complexity is ASSERTED, not assumed: 100k insertions must respect the 0.75 load
factor, re-adding all 100k must not grow the table at all, and a 200-round
add/remove churn must not let tombstones grow the capacity.

src/tests/generics/fail-container-nohash-set.bas pins the missing-HashOf
diagnostic.
