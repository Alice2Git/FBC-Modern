DEFER -- run a statement on the way out
=======================================

    sub Load( byref path as string )
        dim as HANDLE h = CreateFile( path, ... )
        if( h = INVALID_HANDLE_VALUE ) then exit sub

        defer CloseHandle( h )

        ...                              ' any number of early exits
        if( bad ) then exit sub          ' CloseHandle runs
        if( worse ) then return          ' CloseHandle runs
        goto finish                      ' CloseHandle runs
    end sub                              ' CloseHandle runs


WHY IT EXISTS
-------------

FreeBASIC has deterministic destructors, which handle cleanup well -- but only
if you declare a type for every cleanup action. A one-off CloseHandle,
DeleteObject, ReleaseDC or free in a procedure with four early exits gets
written four times, or forgotten once. That is the most common resource-leak
shape in Win32 code, and Win32 code is FreeBASIC's home ground.

DEFER is for the cleanup that does not justify a type.


RULES
-----

    defer <statement>

  - Runs at the exit of the ENCLOSING SCOPE, not of the procedure.
  - Runs in REVERSE registration order.
  - Runs on EVERY path out: falling off the end, 'exit sub', 'exit function',
    'return', 'exit for/while/do' including 'exit for, for', and 'goto' out of
    any number of nested scopes.
  - In a loop body, runs on EVERY ITERATION -- the loop body is a scope.
  - Takes ONE statement. There is no block form.


IT INTERLEAVES WITH DESTRUCTORS
-------------------------------

Defers and local destructors are not two passes. They live in one list in
declaration order and unwind together:

    scope
        dim a as Tr : a.nm = "a"
        defer print "[1]"
        dim b as Tr : b.nm = "b"
        defer print "[2]"
    end scope

    ' [2]  ~b  [1]  ~a

so a defer can rely on a local declared before it still being alive, and a
destructor can rely on a defer registered after it having already run.


THE STATEMENT IS EVALUATED AT EXIT
----------------------------------

Everything the deferred statement reads is read when it RUNS, not when it was
written:

    dim as long v = 7
    defer print v
    v = 9
    ' prints 9

This is the single most common surprise. It matters most in a loop, where it
does not look like a defer question at all:

    dim as long i = 0
    while( i < 3 )
        defer print i        ' prints 1, then 2 -- not 0, then 1
        i += 1
        if( i = 2 ) then exit while
    wend

If you need the value as it was, copy it into a scope-local first.


REGISTRATION IS LEXICAL, NOT DYNAMIC
------------------------------------

This is the one place DEFER here differs from Go's, and it is worth knowing.

The cleanup is derived from the scope's SYMBOL TABLE at compile time. Nothing
is recorded at run time, so a 'defer' that was never "reached" still runs:

    scope
        goto skip
        defer print "runs anyway"        ' error 349
        skip:
    end scope

Because that reads as if the jump skips the defer and it does not, crossing a
DEFER with a branch is refused:

    error 349: Branch crossing a DEFER statement, to label: SKIP

which is the same rule FreeBASIC already applies to jumping past a local with a
constructor. What IS honoured is position: a defer placed after an early exit
never runs on that exit, because it is outside the exit's statement window.

    sub f( )
        print "before"
        exit sub
        defer print "never"              ' correctly does not run
    end sub


NOT AT MODULE LEVEL
-------------------

    defer print "x"      ' error 348: DEFER is not allowed at module level

There is no scope to exit, so nothing would ever run it.


'defer' IS A CONTEXTUAL KEYWORD
-------------------------------

It is NOT a reserved word. Making it one would break every existing program
that uses 'defer' as a name, and a contextual keyword costs nothing to programs
that do not use the feature.

It is read as the keyword only when the NEXT token begins a statement. So all
of this still compiles and behaves exactly as before:

    dim defer as long = 3
    defer = 4
    defer += 5                  ' note: '+=' lexes as '+' then '='
    dim deferArr( 0 to 2 ) as long
    type T : as long defer : end type
    h.defer = 5
    x = defer( 6 )              ' a function named 'defer'

THE ONE INCOMPATIBILITY: a PAREN-LESS call in statement position to a sub named
'defer':

    defer 6                     ' now a DEFER of the statement '6'
    defer( 6 )                  ' still a call

Every call that produces a value is unaffected, because it needs the
parentheses anyway. This is the same trade FOR EACH already makes with 'each'.


DIAGNOSTICS
-----------

    error 347: DEFER requires a statement
    error 348: DEFER is not allowed at module level
    error 349: Branch crossing a DEFER statement


IMPLEMENTATION
--------------

A DEFER is registered as a hidden VAR symbol in the current scope, carrying the
already-parsed statement.

That is the whole design. Cleanup in fbc is not a list of statements -- it is
DERIVED from the scope's symbol table, walked tail-to-head, acting on every
entry that needs cleanup. Registering a symbol therefore gets reverse order,
interleaving with destructors, the statement-number window and multi-scope
'goto' exits from machinery that already existed for destructors. The three
consumption sites needed no knowledge of DEFER beyond one branch each.

Two consequences worth recording:

  - The statement is parsed ONCE and cloned per exit. It is held as a CHAIN of
    nodes, not a single tree: one source statement can lower to several linked
    nodes (a call plus the destruction of its temporaries), and the cloning
    helper follows only child links, so cloning just the head would silently
    drop the rest.

  - A defer symbol is a VAR but names NO STORAGE, so it must be skipped
    wherever variables are allocated or emitted. Only the ASM/gas64 backend
    allocates every local, so missing this would have been a gas64-only defect.

Source: src/src/compiler/parser-defer.bas, symbAddDefer( ) in symb-var.bas.


TESTS
-----

src/tests/generics/defer.bas is exhaustive: reverse order, fallthrough off
'end scope' / 'end sub' / 'end function', every break path including
'exit for, for' and 'goto' out of three nested scopes, a loop body, defers in
IF / SELECT / WITH arms, interleaving with destructors asserted in BOTH orders
and on BOTH the fallthrough and break paths, a defer that is never reached, and
backward compatibility for 'defer' as a variable, array, field and shared.

Order is asserted by accumulating into a string and comparing the exact
sequence. A defer that runs at the wrong time still runs, so only the sequence
distinguishes right from wrong.

src/tests/generics/defer-identifier.bas covers 'defer' as a PROCEDURE name --
separate, because FreeBASIC refuses a local that shadows a module-level
procedure of the same name.

src/tests/errors/defer-errors.bas holds the golden output for all three
diagnostics, on all five targets.
