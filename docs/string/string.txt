FB.* -- the string algorithms FreeBASIC does not ship
=====================================================

    #include once "fb/string.bi"
    using FB

    print Replace( "Hello World", "World", "Earth" )   ' Hello Earth
    print Tally( "a,b,c", "," )                        ' 2
    print PadLeft( "42", 6, "0" )                      ' 000042
    print Between( "log(42) end", "(", ")" )           ' 42

    dim parts as Array( of string ) = Split( "a,b,c" )
    print parts.Count( )                               ' 3
    print Join( parts, " | " )                         ' a | b | c


WHY IT EXISTS
-------------

FreeBASIC ships LEFT, RIGHT, MID, INSTR, INSTRREV, TRIM, UCASE, LCASE, SPACE
and STRING, and stops. There is no Replace, no Split, no Join, no pad, and no
way to work with a set of characters. Every program that needs them writes them
again, usually with a 'redim preserve' loop that is quadratic.

These 37 functions are the portable half of the AfxNova string library
(AfxStr.inc and DWStrProcs.inc) -- two decades of use, but Windows-only, tied to
WSTRING and DWSTRING, and in places built on COM.

NOTHING HERE IS A KEYWORD. Replace, Contains, Split and the rest stay available
as your own identifiers until you write 'using FB'. The language is unchanged.


ALL FOUR STRING TYPES
---------------------

Every function is declared three times -- STRING, WSTRING, USTRING -- and
ZSTRING is served by the STRING overload through fbc's own conversion, which for
bytes to bytes is exact and involves no locale. You never name which family you
are in; the first argument decides.

There is no dynamic ZSTRING or WSTRING, so a function cannot return the type it
was handed:

    string, zstring   ->  string        bytes, no encoding assumed
    wstring, ustring  ->  ustring       UTF-16 on every target

A WSTRING in giving a USTRING out is the surprising one. It is also the only
answer available: a fixed-length result would need a buffer the caller has not
supplied. On Windows it costs nothing to use, because a ustring already is
UTF-16.

EVERY PARAMETER AFTER THE FIRST IS A USTRING, in all three overloads. That is
forced, not preferred. fbc ranks an overload on all of its parameters, so with
per-family types on the second one,

    Tally( someWstring, "abc" )        ' error 98: Ambiguous call

is an ambiguity rather than a choice. One shared type on the later parameters
moves the whole decision onto the first.

The cost is that a pattern handed to the BYTE family is converted UTF-8 ->
UTF-16 -> UTF-8 on the way in. For an ASCII or UTF-8 pattern that is exact, and
for a literal it costs nothing at run time -- fbc converts string literals to
ustring at compile time. It does not survive a pattern of arbitrary non-UTF-8
bytes; searching binary for a raw byte sequence is outside what this library
does, and USTRING draws the same line. The haystack is never converted, so byte
positions in a STRING stay byte positions.


CODE UNITS, POSITIONS, AND CASE
-------------------------------

Positions and lengths count CODE UNITS, matching LEN, [] and INSTR. On the wide
family an astral character is a surrogate pair and counts as 2. A search can
never land mid-character -- a surrogate half cannot equal a BMP unit -- though
MID can still split one, as it always could.

POSITIONS ARE 1-BASED, and 0 means "not found", matching INSTR. This is NOT the
zero-based convention FB.Array uses. Strings and containers are different worlds
and each keeps its own tradition.

A start below 1 is invalid and answers 0 (or "" for a function returning text)
rather than clamping, so a position fed back in from a call that returned "not
found" cannot silently restart the scan. AfxNova reads a negative start as
counting from the right; that reading and this one claim the same range, so only
one could survive, and consistency won.

'ignoreCase' folds ASCII only on the byte family, because a STRING is a byte
buffer with no declared encoding and folding above 127 would be guessing at a
codepage. The wide family folds through the generated simple BMP table, so it
gives the same answer on every machine and in every locale.

ON THE BYTE FAMILY A CHARACTER SET IS A SET OF BYTES. InstrChars, TallyChars,
VerifySet, SpanOf, RemoveChars, RetainChars, ReplaceChars and SplitChars compare
one unit at a time, and on a STRING a unit is a byte. Put a multi-byte character
in the set and each of its bytes joins separately:

    dim as string s = "xx" & chr(&hC3) & chr(&hA9) & "yy"    ' UTF-8
    InstrChars( 1, s, wchr(&hE8) )      ' 3 -- matched the C3 byte

A STRING carries no encoding, so the set cannot be decoded into characters. Use
the ustring overload for character sets over non-ASCII text; there a set member
is one code unit and the answer is 4. The substring functions are unaffected on
both families: they match whole sequences and are exact for any UTF-8 pattern.


THE FUNCTIONS
-------------

n is the input length, m the pattern length.

  SEARCH AND INSPECT                                          returns

    Tally( s, match [, ic] )                     O(n*m)   long
        Non-overlapping occurrences. "aaaa" contains "aa" TWICE.
    TallyChars( s, chars [, ic] )                O(n*k)   long
    InstrChars( start, s, chars [, ic] )         O(n*k)   long
    VerifySet( start, s, chars [, ic] )          O(n*k)   long
        First position NOT in the set, or 0 if every one is.
    SpanOf( start, s, chars [, ic] )             O(n*k)   long
    StartsWith( s, prefix [, ic] )               O(m)     boolean
    EndsWith( s, suffix [, ic] )                 O(m)     boolean
    Contains( s, match [, ic] )                  O(n*m)   boolean

  EXTRACT

    Extract( start, s, match [, ic] )            O(n*m)   text before match
    ExtractChars( start, s, chars [, ic] )       O(n*k)
    Remain( s, match [, start] [, ic] )          O(n*m)   text after match
    RemainChars( s, chars [, start] [, ic] )     O(n*k)
    Between( s, open, close [, start] [, ic] )   O(n*m)
    ClipLeft( s, count )                         O(n)
    ClipRight( s, count )                        O(n)
    DeleteAt( s, start, count )                  O(n)
    InsertAt( s, insert, position )              O(n)

  TRANSFORM

    Replace( s, match, with_ [, ic] )            O(n*m)
    Remove( s, match [, ic] )                    O(n*m)
    RemoveChars( s, chars [, ic] )               O(n*k)
    RetainChars( s, chars [, ic] )               O(n*k)
    ReplaceChars( s, chars, with_ [, ic] )       O(n*k)   length is invariant
    RemoveBetween( s, open, close
                   [, all] [, start] [, ic] )    O(n*m)
    Reverse( s )                                 O(n)
    Repeat( count, s )                           O(n*count)
    Shrink( s [, mask] )                         O(n*k)
    MCase( s )                                   O(n)     title case

  PAD, WRAP, ESCAPE, PREDICATES

    PadLeft( s, width [, pad] )                  O(width)
    PadRight( s, width [, pad] )                 O(width)
    PadCenter( s, width [, pad] )                O(width)
    Wrap( s [, open] [, close] )                 O(n)
    Unwrap( s [, open] [, close] [, ic] )        O(n)
    Escape( s )                                  O(n)
    Unescape( s )                                O(n)
    IsNumeric( s )                               O(n)     boolean
    IsBlank( s )                                 O(n)     boolean

  SPLIT AND JOIN

    Split( s [, delim] [, ic] )                  O(n*m)   Array( of T )
    SplitChars( s [, chars] [, ic] )             O(n*k)   Array( of T )
    Join( parts [, delim] )                      O(total) text


THE RULES THAT ARE EASY TO GET WRONG
------------------------------------

Each of these has a defensible opposite, so each is a decision rather than an
accident, and each is asserted in the test suite.

EMPTY ARGUMENTS

    Tally( s, "" )              0     a zero-width match advances nothing
    InstrChars( n, s, "" )      0     "find one of nothing" cannot succeed
    VerifySet( n, s, "" )       n     "find one NOT among nothing" cannot fail
    SpanOf( n, s, "" )          0     nothing is in the set, so the run is empty
    StartsWith( s, "" )         true  vacuous, including for s = ""
    Contains( s, "" )           true  same
    RemoveChars( s, "" )        s     an empty set removes nothing
    RetainChars( s, "" )        ""    and so keeps nothing -- the complement
    Shrink( s, "" )             s     there is nothing to shrink
    Split( s, "" )              one field, the whole string

EXTRACT AND REMAIN MISS DIFFERENTLY, on purpose:

    Extract( 1, s, missing )    the whole remainder
    Remain( s, missing )        ""

Extract's rule is what makes a parse loop terminate cleanly -- the final field
has no trailing delimiter, and this hands it back instead of dropping it.
Remain's is the only honest answer to "everything after X" when there was no X.

SPLIT NEVER DROPS A FIELD. N delimiters give N+1 fields, always:

    Split( "a,,c" ) -> 3      Split( ",a" ) -> 2      Split( "" ) -> 1

That is what makes Join( Split( s, d ), d ) equal s for every s.

INVALID ARGUMENTS ARE NO-OPS, not errors and not truncation. DeleteAt with a
start past the end, or a count of zero, returns the string unchanged; InsertAt
with a position below 1 does the same. A pad width of 0 or less gives "".

ONE UNIT MEANS ONE UNIT. ReplaceChars maps a single unit to a single unit, so
'with_' must be exactly one; anything else -- empty, longer, or an astral
character, which is two units -- returns the string unchanged rather than
writing half a character. The pad functions take the same rule with a softer
failure: a pad that is not one unit pads with a SPACE, because a pad function
that pads with nothing is useless while a substitution that substitutes nothing
is merely inert.


REVERSE IS THE ONE FUNCTION WHOSE FAMILIES DISAGREE
---------------------------------------------------

On the wide family SURROGATE PAIRS ARE KEPT INTACT. A ustring is UTF-16 by
definition, so reversing its code units blindly would emit a low surrogate
before its high one -- invalid UTF-16 every time an astral character is present,
not occasionally.

On the byte family bytes reverse as bytes, which does mangle multi-byte UTF-8. A
STRING has no declared encoding, so there is no pair to recognise and no way to
know whether there would be one. Reverse UTF-8 text through the ustring
overload.


ESCAPE
------

Backslash escaping -- what makes a string safe to write between quotes in a
config file, a log line, or generated source, and reversible afterwards.

    \  "             ->  \\  \"
    LF CR TAB NUL    ->  \n  \r  \t  \0
    other units below 32, and 127   ->  \xHH
    everything else, INCLUDING ALL NON-ASCII, passes through

Non-ASCII is left alone deliberately: escaping it would make a ustring
unreadable and reduce a UTF-8 STRING to a wall of hex, and the job is to
neutralise what breaks quoting, not to force the text to ASCII.

Unescape is the exact inverse. Unescape( Escape( s ) ) is s for every input,
including one that already contains backslashes -- verified over every byte
value 0..255. An unrecognised escape yields the escaped character ("\q" -> "q");
a trailing lone backslash is kept, since nothing follows it to unquote.


WHERE THIS DIFFERS FROM AfxNova
-------------------------------

Eleven deliberate divergences. Everything else answers what AfxNova answers.

 1. Remove is a SINGLE PASS -- exactly Replace with an empty replacement.
    AfxStrRemove restarts its search at position 1 after each deletion, so
    removals cascade: deleting "ab" from "aabb" leaves "" there, because the
    deletion creates a match that was not in the input. Here it leaves "ab".
    Also O(n) rather than O(n^2).

 2. Reverse keeps surrogate pairs intact on the wide family. AfxStrReverse
    swaps code units and produces invalid UTF-16 for any astral character.

 3. Unwrap requires BOTH ends and removes ONE of each. AfxStrUnWrap uses
    LTRIM/RTRIM with the delimiter, so it strips repeated occurrences and does
    not need a pair -- "'''x'''" loses all six quotes and "'x" loses its opener
    with nothing matching it. Stripping a delimiter that was never balanced is
    how a quoted field containing a quote gets silently mangled.

 4. Shrink with an EMPTY mask returns the input unchanged. AfxStrShrink returns
    the empty string, which reads like a guard clause that fell through to the
    wrong variable.

 5. MCase starts a word after any NON-ALPHANUMERIC character. DWStrMCase tests
    against a fixed punctuation list, so it capitalises after "." and "-" but
    not after "/", "_" or a tab -- gaps rather than decisions.

 6. IsNumeric asks whether the string IS a number, with a real grammar.
    AfxIsNumeric asks whether every character is drawn from "+-.0123456789",
    which makes "++--.." numeric; that is a character-set test, and RetainChars
    already does those. Radix literals (&H, &O, &B) are not accepted here.

 7. Escape is BACKSLASH escaping. AfxNova's DWStrEscape escapes REGULAR
    EXPRESSION metacharacters so a literal can be used as a pattern -- it is
    built on CRegExp, a COM class, and is only meaningful beside a regex engine.
    There is none here, so it would have had no consumer.

 8. InsertAt with a position below 1 returns the string unchanged.
    AfxStrInsert's comment says such a position appends; its code returns the
    string untouched. The code is followed, because appending on a negative
    index is the kind of silent success that hides a caller's off-by-one.

 9. A negative start is NOT counted from the right. Positions below 1 are
    invalid throughout, and the two readings claim the same range.

10. DeleteAt is one function. AfxStrClipMid and AfxStrDelete are the same
    algorithm under two names.

11. Wrap and Unwrap take an EMPTY 'close' to mean "same as open", which
    collapses AfxNova's three overloads into one function.

TWO MORE ARE AfxNova BUGS, found by the differential harness in
tests/afxnova_differential.bas. Both are cases where the code contradicts its
own comment, so "divergence" here means this library does what AfxNova
documents and AfxNova does not.

12. TallyChars does not double-count a repeated character in the set.
    AfxStrTallyAny's dedup loop seeds its working copy with the whole match
    string and then tests INSTR( copy, <char> ) against ITSELF, so every
    character is always found and nothing is ever removed -- the loop is a
    no-op. Its comment promises "repeated characters in wszMatchStr will not
    increase the count"; TallyChars( "abacadabra", "aa" ) is 5 here and 10
    there.

13. ExtractChars returns the whole remainder on a miss, like Extract.
    AfxStrExtractAny ends in an unconditional empty return, contradicting both
    its own comment ("If wszMatchStr is not present ... then all of wszMainStr
    is returned") and its sibling AfxStrExtract, which does return the
    remainder.

Excluded entirely, as Windows-only or COM-bound: locale and country names,
month and day names, LCMapStringEx casing, CryptBinaryToString, BSTR,
environment access, PathName/PathScan, and the byte-size and time-interval
formatters.


IMPLEMENTATION
--------------

The algorithms live in src/rtlib/str_ops_core.h and are written ONCE, then
instantiated twice -- str_ops.c at byte width, ustr_ops.c at 16-bit -- the same
pattern con_print_raw_uni.h and ustr_wchar_conv.h already use. Two
hand-maintained copies of a search loop drift, and the drift shows up as one
width quietly disagreeing with the other on an edge case nobody tests twice.

Reached from FreeBASIC through 'extern "C" declare ... alias' inside namespace
FB -- the pattern inc/string.bi already uses for FORMAT. Note that 'alias' alone
is not enough inside a namespace: without the nested extern "C", fbc mangles
right past it, and a nested namespace does not inherit an enclosing one either.

Split, SplitChars and Join are the only ones with FreeBASIC bodies, because
their result is an Array( of T ) that the runtime cannot build. They are
'private', so each including module gets its own copy and two modules including
the header still link -- the same trade the generic containers make. The C side
returns field boundaries rather than strings, so a split is two linear passes
instead of the ParseCount-then-Parse-in-a-loop shape, which rescans from the
start for every field and is quadratic.


ONE UPSTREAM FreeBASIC BUG WORTH KNOWING
----------------------------------------

LEN cannot parse a NAMESPACE-QUALIFIED function call:

    print len( FB.Replace( s, "a", "b" ) )    ' error 42: Variable not declared

This is not specific to this library, or to USTRING, or to FBC-Modern -- stock
fbc 1.10.1 fails identically on

    namespace NS
        function Twice( byref s as const string ) as string : ... : end function
    end namespace
    print len( NS.Twice( t ) )

Both workarounds are ordinary: write 'using FB' and drop the qualifier, or
assign the result first and take LEN of the variable. It is mentioned here only
because the qualified spelling is the natural one to reach for before
discovering 'using', and the error message points nowhere near the cause.


DIALECTS
--------

-lang fb only. The library uses namespaces, and Split returns a generic
container. The header says so with #error rather than failing obscurely.
