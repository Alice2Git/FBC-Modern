# RFC-0005 — ISO 8601 / RFC 3339

Status: **draft** · Phase 5 · Depends on: [RFC-0001](RFC-0001-core-representation.md), [RFC-0002](RFC-0002-timespan.md)

The highest-value item in [ranked-gaps.md](ranked-gaps.md). Neither FreeBASIC
nor AfxNova can emit or parse ISO 8601, which is what JSON, HTTP, SQL, logs and
every web API speak. Every FB program that talks to anything modern hand-rolls
this today.

Entirely locale-independent, entirely ASCII, entirely in portable C. Every test
in §6 asserts an exact string in both directions.

## 1. Emitted forms

Emission is **canonical and single-valued** — one input produces exactly one
string. The variety in ISO 8601 is accepted on input only.

| Type | Method | Output |
|---|---|---|
| `Instant` | `ToIsoString()` | `2025-03-04T14:30:05.1234567Z` |
| `DateTime` (offset) | `ToIsoString()` | `2025-03-04T14:30:05.1234567+05:30` |
| `DateTime` (UTC) | `ToIsoString()` | `2025-03-04T14:30:05.1234567Z` |
| `DateTime` (unspecified) | `ToIsoString()` | `2025-03-04T14:30:05.1234567` |
| `LocalDate` | `ToIsoString()` | `2025-03-04` |
| `LocalTime` | `ToIsoString()` | `14:30:05.1234567` |
| `TimeSpan` | `ToIsoString()` | `P1DT2H3M4.5S` |

Rules:

- Extended format only — the separators are always present. Basic format
  (`20250304T143005Z`) is accepted on input, never emitted.
- `T` is the date/time separator, always uppercase.
- Year is always four digits, zero-padded. This is why RFC-0001 caps the range
  at 9999.
- The fractional part is **omitted entirely** when the sub-second tick count is
  zero, and otherwise emitted with **exactly seven digits**, no trailing-zero
  trimming. Fixed width makes the output lexicographically sortable, which is
  the property that matters when these strings land in a log or a database key.
- Offset is `±HH:MM`, always with the colon and always two-digit. `Z` is emitted
  for UTC, never `+00:00`.
- An `Invalid` value emits the empty string (RFC-0001 §3 rule 5).

`ToIsoString` never fails and never allocates unboundedly — the maximum output
is 33 bytes and the C core writes into a caller-supplied buffer.

## 2. Accepted forms

`TryParse` is **strict** — it accepts the ISO 8601 profile below and rejects
everything else. There is no locale, no guessing, and no partial acceptance.
Trailing characters are an error.

```
date        = YYYY "-" MM "-" DD              ; extended
            | YYYYMMDD                        ; basic
            | YYYY "-" DDD | YYYYDDD          ; ordinal date
            | YYYY "-W" ww "-" d | YYYYWwwd    ; ISO week date

time        = hh ":" mm [ ":" ss [ frac ] ]   ; extended
            | hhmm[ss[frac]]                  ; basic
frac        = ( "." | "," ) 1*DIGIT           ; comma is legal ISO 8601

offset      = "Z" | "z"
            | ( "+" | "-" ) hh [ ":" ] [ mm ]

datetime    = date ( "T" | "t" | " " ) time [ offset ]
```

Notes on each concession:

- **Basic format** is accepted because compact timestamps appear in filenames
  and older protocols.
- **Ordinal and week dates** are accepted because they are ISO 8601 and cost
  little once the calendar kernel from RFC-0004 exists.
- **Comma as decimal separator** is the ISO 8601 preferred form, and appears in
  European data.
- **A space instead of `T`** is not ISO 8601 but is RFC 3339 §5.6's explicit
  allowance, and is what every SQL database emits. Rejecting it would make the
  parser useless against real data.
- **Lowercase `t` and `z`** are RFC 3339's allowance.
- A **two-digit-hour-only offset** (`+05`) is ISO 8601; `+0530` without the
  colon is too.

Explicitly **rejected**:

- Two-digit years. Ever. There is no century-inference rule and there will not
  be one.
- `24:00` as end-of-day. It is legal ISO 8601 and it is a landmine; the value it
  denotes is representable as the next day's `00:00` and the caller should say
  so.
- Negative years, expanded years (`+002025`), and years past 9999 — outside the
  range of RFC-0001.
- Leap seconds (`:60`). Out of scope per [rationale.md](rationale.md).
- More than 7 fractional digits are **truncated**, not rejected — a nanosecond
  timestamp from another system parses, losing the sub-tick digits. This is the
  one lenient behaviour in the parser and it is deliberate: rejecting
  `…T00:00:00.123456789Z` would fail against Go and Rust output.

## 3. `TryParse`

```freebasic
declare static function TryParse( byref s as string, byref result as DateTime ) as boolean
declare static function TryParseIso( byref s as string, byref result as DateTime ) as boolean
declare static function ParseIso( byref s as string ) as DateTime   ' Invalid on failure
```

Contract, normative:

1. Returns `true` and assigns `result` on success.
2. Returns `false` and assigns `result = Invalid` on failure. `result` is
   **always written**, so a caller who ignores the return value still cannot
   read a stale value.
3. Never raises an `err()`, never throws, never writes to stderr.
4. Leading and trailing ASCII whitespace is trimmed before parsing. Interior
   whitespace, other than the single RFC 3339 space separator, is an error.
5. An empty or all-whitespace input is a failure, not a zero value.
6. Parsing is byte-oriented ASCII. A UTF-8 BOM is not skipped; it is an error.

Each type gets the same trio. Offset handling on `DateTime.TryParseIso`:

| Input has | Result offset |
|---|---|
| `Z` | UTC |
| `±HH:MM` | that offset |
| nothing | `DT_OFFSET_UNSPECIFIED` |

`Instant.TryParseIso` **requires** an offset — a string with none is a failure,
because there is no way to place a naive reading on the UTC timeline without
guessing. This is the type system doing its job.

## 4. Round-trip guarantee

**Normative:** for every valid value `v` of every type in §1,

```
T.ParseIso( v.ToIsoString() ) = v
```

exactly — same ticks, same offset. This is the property phase 5 exists to
deliver and the one §6 tests hardest.

The converse does not hold: `ParseIso` then `ToIsoString` is *not* the identity
on strings, because canonical emission normalizes basic format, ordinal dates,
comma separators and `+00:00`. What does hold is **fixed point after one round**:

```
s2 = ParseIso( s1 ).ToIsoString()
s3 = ParseIso( s2 ).ToIsoString()
s2 = s3
```

## 5. `TimeSpan` durations

Grammar, ISO 8601 §4.4.3.2:

```
duration = [ "-" ] "P" [ nD ] [ "T" [ nH ] [ nM ] [ n[.n] S ] ]
```

- Weeks (`P2W`) are accepted on input and converted to 14 days; never emitted.
- Years and months (`P1Y2M`) are **rejected**. A `TimeSpan` is a fixed
  duration (RFC-0002 §1) and a month has no fixed length. Accepting `P1M` would
  require inventing a length, and every invented answer is wrong somewhere.
- `PT0S` is the canonical zero. A bare `P` is an error.
- The sign is a single leading `-` applying to the whole duration; per-component
  signs are an error.
- Emission puts the fractional part on the seconds component only, with trailing
  zeros trimmed (`PT4.5S`, not `PT4.5000000S`) — durations are not sorted as
  strings, so fixed width buys nothing here. This is the one place emission
  differs from §1's rule, and it is intentional.

## 6. Tests

Suite `fbc_tests.chrono.iso`.

**Exact emission** — as implemented this is **38** exact-string assertions, not
the 60 an earlier draft asked for. The number was arbitrary; what matters is
covering every *structural* case, and 22 more hand-written rows would only
re-cover the value space that the 100,000-value round-trip below covers far
better. The structural cases, all present:
zero and max ticks; sub-second zero (no fractional part) and sub-second
non-zero (seven digits); a value whose fraction ends in zeros
(`.1000000` — must **not** be trimmed); UTC, positive offset, negative offset,
half-hour offset (`+05:30`), 45-minute offset (`+05:45`), unspecified; year 1
and year 9999; every type in §1.

**Exact parse** — a table of at least 100 accepted inputs × expected ticks and
offset, covering every production in §2: extended, basic, ordinal, week date,
comma fraction, space separator, lowercase `t`/`z`, `+05`, `+0530`, 1 through 9
fractional digits (with 8 and 9 asserted as *truncating*, not rounding).

**Rejection corpus** — **34** inputs plus 6 positive controls, each asserted to
return `false` *and* leave `result` `Invalid` (again, the earlier "at least 60"
was arbitrary; these are the distinct *failure modes*, not padding): empty; whitespace only; `2025-13-01`; `2025-02-30`;
`2025-02-29` (non-leap); `2024-02-29` (must *pass* — the control);
`25-03-04`; `2025-03-04T24:00:00`; `2025-03-04T23:59:60`; `2025-03-04T14:30:05+19:00`
(offset > 18 h); `2025-03-04 14:30:05 ` with interior double space;
`2025-03-04T14:30:05Zx` (trailing garbage); `+002025-03-04`; `2025-03-04T`;
`T14:30:05`; a UTF-8 BOM prefix; `2025-W54-1`; `2025-367`.

**Round trip, exhaustive-ish** — 12,500 values from a fixed seed spanning the
whole tick range × an 8-entry offset set {UTC, unspecified, −18:00, −05:00,
+00:00, +05:30, +05:45, +18:00} = 100,000 round trips, asserting
`ParseIso( ToIsoString( v ) ) = v` exactly in both ticks and offset. Fixed seed
so a failure is reproducible. (+18:00 rather than +14:00: the offset field's
documented limit is ±18:00, so the boundary is the value worth testing.)

**String fixed point** — for the whole accepted-input table, assert
`s2 = s3` per §4.

**`Instant` requires an offset** — `2025-03-04T14:30:05` fails on
`Instant.TryParseIso` and succeeds on `DateTime.TryParseIso`.

**Duration** — emission and parse tables; `P2W` → 14 days; `P1Y` and `P1M`
rejected; `PT0S` round-trips; negative durations; trailing-zero trimming
asserted (`PT4.5S`).

**No locale leakage** — the whole suite runs a second time after setting a
non-English locale, asserting byte-identical results. This is the test that
catches an accidental `sprintf( "%f" )` picking up a comma decimal point, which
is a real and easy bug on a European machine.

Both backends, both platforms.
