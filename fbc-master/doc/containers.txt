STANDARD CONTAINERS -- Array, Map, Set, LinkedList
==================================================

    #include once "containers.bi"
    using FB

    dim names as Array( of string )
    dim ages  as Map( of string, long )
    dim seen  as Set( of long )
    dim queue as LinkedList( of string )

Four containers, written in ordinary FreeBASIC on top of generics, the iterator
protocol and FOR EACH. None is built into the compiler and none gets special
treatment from it: a better one written by anybody else is on exactly equal
footing.

They live in NAMESPACE FB. Nothing is added to the global namespace, so a
program that already defines its own Array, Map, Set or List is unaffected until
it says 'using FB'. containers.bi is not included by default.

The pieces can be included individually: fb/array.bi, fb/map.bi, fb/set.bi,
fb/linkedlist.bi, and fb/hash.bi.


WHY
---

FreeBASIC had no growable array, no hash map, no set and no list. What existed
was 'redim preserve', which reallocates and copies on EVERY call, so the
idiomatic append is quadratic:

    redim preserve arr( 0 to ubound( arr ) + 1 )     ' O(n^2) over a loop
    arr( ubound( arr ) ) = newItem

and for hash maps the available answer was a COM Scripting.Dictionary --
Windows-only, CoInitialize per instance, every key and value a VARIANT, every
lookup a late-bound IDispatch call.


THREE THINGS TO READ FIRST
--------------------------

1. ARRAY INDICES ARE ZERO-BASED. A deliberate break with 'dim arr(1 to 10)'
   tradition, because Count and index arithmetic are otherwise a permanent
   source of off-by-one.

2. MAP'S INDEXER INSERTS ON A MISS.

       m[ k ] += 1              ' works, and is why the indexer inserts
       if m[ k ] = 0 then       ' silently GROWS the map -- use TryGet

   Use TryGet or Contains to read. Every language has this argument.

3. COPY AND ASSIGNMENT ARE DEEP for all four. That is the only rule consistent
   with FreeBASIC's value semantics, and there is no move constructor in the
   language to make it cheap. Pass containers BYREF where it matters. A
   container of pointers frees the container, not the pointees.


Array( of T )
-------------

    Count( )                  O(1)
    Capacity( )               O(1)
    IsEmpty( )                O(1)
    a[ i ]                    O(1)   byref, and an lvalue
    At( i )                   O(1)   byref; for READING and byref arguments
    Push( v )                 amortised O(1)
    Pop( )                    O(1)   removes and returns the last
    Insert( i, v )            O(n)
    Remove( i )               O(n)   preserves order
    RemoveSwap( i )           O(1)   does NOT preserve order
    Clear( )                  O(n)   drops elements, KEEPS capacity
    Reserve( n )              O(n)
    Shrink( )                 O(n)   releases unused capacity
    GetIterator( )            O(1)

    Sort( a )                 free procedure, needs '<' on T
    IndexOf( a, v )           free procedure, needs '=' on T; -1 if absent
    Contains( a, v )          free procedure, needs '=' on T

Capacity doubles from 8. It never shrinks on its own -- a push/pop loop sitting
on a boundary would thrash -- so Shrink( ) is explicit.

At( ) is not usable as an assignment target in statement position:
'a.At( 1 ) = 11' parses as an equality expression and warns. That is a
FreeBASIC rule about byref function results. Use a[ 1 ] = 11 to write.

Sort, IndexOf and Contains are FREE PROCEDURES, not members, and that is not a
style choice. Every member of a generic is instantiated whether it is called or
not, so a member needing '=' on T would make the whole type unusable for any T
without one -- Array( of Array( of long ) ) could not be instantiated at all.
As free procedures the requirement lands on the call that needs it.

One consequence of strict type-argument inference: an untyped literal is an
INTEGER, so IndexOf( nums, 3 ) over an Array( of long ) cannot infer T. Write
IndexOf( nums, 3L ), or pass a variable.

Sort is a Shell sort over Ciura's gaps: in-place, no recursion, no pivot policy,
about O(n^1.3) in practice rather than O(n log n) in the worst case.


Map( of K, V )
--------------

    Count( ) / IsEmpty( ) / Capacity( )       O(1)
    m[ k ]                    avg O(1)   byref, an lvalue, INSERTS ON MISS
    Add( k, v )               avg O(1)   false if present; does NOT overwrite
    Put( k, v )               avg O(1)   insert or overwrite; true if new
    TryGet( k, out )          avg O(1)   no insertion on a miss
    Contains( k )             avg O(1)   no insertion
    Remove( k )               avg O(1)   true if something went
    Clear( ) / Reserve( n )   O(n)
    Keys( ) / Values( )       O(n)       snapshots, as Array( of ... )
    GetIterator( )            O(1)       yields KeyValuePair( of K, V )

Open addressing with linear probing, power-of-two capacity, tombstones on
removal, load factor 0.75, rehash doubles. Rehashing drops tombstones, so an
add/remove churn loop does not fill the table with them.

ITERATION ORDER IS UNSPECIFIED and changes across insertions. It is not
randomised per process.

    for each kv in ages
        print kv.key, kv.value
    next

The pair is assembled by the iterator and does not live in the map, so writing
to it changes nothing. Use m[ k ] to write.


Set( of T )
-----------

    Count( ) / IsEmpty( ) / Capacity( )       O(1)
    Add( v )                  avg O(1)   FALSE if already present
    Contains( v )             avg O(1)
    Remove( v )               avg O(1)
    Clear( ) / Reserve( n )   O(n)
    UnionWith( other )        O(|other|)
    IntersectWith( other )    O(n)
    ExceptWith( other )       O(|other|)
    Items( )                  O(n)       snapshot, as Array( of T )
    GetIterator( )            O(1)

Add returning FALSE when the element was already there is what makes

    if seen.Add( x ) then ...

the natural spelling of "process each thing once".

Value( ) is byref so 'for each byref' compiles, but DO NOT modify an element in
place: changing it changes its hash and it can never be found again. Remove and
re-Add.


LinkedList( of T )
------------------

    Count( ) / IsEmpty( )     O(1)
    PushFront( v )            O(1)
    PushBack( v )             O(1)
    PopFront( ) / PopBack( )  O(1)   removes and returns
    Front( ) / Back( )        O(1)   byref
    Clear( )                  O(n)
    GetIterator( )            O(1)

Doubly linked. Here because Array cannot give O(1) insertion at the front and
because a LinkedList iterator stays valid across insertions elsewhere. It is the
least important of the four -- prefer Array unless front insertion or iterator
stability is what you actually need.

Popping or reading an empty list returns a default-constructed T. There is no
error channel; check IsEmpty( ) first if the difference matters.


THE HASH CONTRACT
-----------------

Map keys and Set elements must be hashable:

    FB.HashOf( k )       must resolve
    k = k                must compare
    EQUAL KEYS MUST PRODUCE EQUAL HASH CODES

The converse is not required -- collisions are handled. Overloads are supplied
for every built-in type: all integers, both floats, pointers, string, zstring
and wstring. Strings hash by CONTENT, and +0.0 / -0.0 hash the same because they
compare equal.

A user type is made hashable by RE-OPENING the namespace:

    type PairKey
        as long a, b
    end type

    operator = ( byref x as PairKey, byref y as PairKey ) as boolean
        return (x.a = y.a) andalso (x.b = y.b)
    end operator

    namespace FB
        function HashOf overload ( byref k as PairKey ) as ulongint
            return HashOf( k.a ) xor (HashOf( k.b ) shl 1)
        end function
    end namespace

Derive the hash only from the fields '=' compares, or equal keys will hash
differently and the map will lose entries.

A key type with no overload fails at the INSTANTIATION site naming HashOf:

    error 99: No matching overloaded function, HASHOF()
      in instantiation of 'Map( of NOHASH, long )'

That is what unconstrained generics can offer today, and it is the strongest
single argument for adding constraints later.

Why an overloaded function rather than a HashCode( ) member: a member cannot be
added to 'long' or 'string', and a generic body cannot branch on its type
parameter -- 'typeof( T )' inside a generic sees the parameter, not what it is
bound to. Ordinary overload resolution at the instantiation site is the
mechanism that works.


ITERATOR INVALIDATION
---------------------

Nothing detects a violation.

    Array         Push causing reallocation             all invalidated
    Array         Insert/Remove/RemoveSwap/Clear/
                  Reserve/Shrink/Sort                   all invalidated
    Array         assignment through [ ]                valid
    Map/Set       Add/Put causing rehash                all invalidated
    Map/Set       Remove                                all invalidated
    LinkedList    PushFront/PushBack                    valid
    LinkedList    removing the node an iterator is on    that one invalidated


TESTS
-----

tests/generics/container-array.bas, container-map.bas, container-set.bas and
container-linkedlist.bas are exhaustive: every member, empty/one/many states,
boundary indices, the growth path, every removal form followed by re-insertion,
deep copy and assignment independence in both directions, destructor balance
with a counting element type, element types including strings, UDTs and nested
containers, and both FOR EACH binding forms.

Complexity is ASSERTED, not assumed: 100k appends must produce O(log n)
reallocations and a capacity under 2n, and 100k map insertions must respect the
load factor. That is the entire point of the library.

Four fail-tests pin the diagnostics for a missing HashOf, '=' and '<'.
